# Build-pinned native adapter

These names belong only to Steam build 25672315. Plugin startup checks both GameAssembly.dll and IL2CPP metadata SHA-256 before resolving the hooks.

## Audit corrections verified against recordings (0.1.12)

The first real session contains 971 legacy results, 55 paired previews and 42 eligible exchanges. All 11 mismatch labels were caused by the observer's incorrect overkill cap. `ObjectTookDamageEventArgs.damage` retains full damage, including overkill (e.g. 342 against 165 remaining HP). Compare it directly to the native preview range. Health subtraction remains capped separately. Full replay through the production evaluator preserves all prior matches and produces 42 matches; it does not replay native combat or RNG.

Before registering a command or step, require the same battle pointer as `elb.ckia.ckic` and the same queue pointer as that battle's `clhf`. Foreign simulations cannot consume the shown preview or replace a pending command. The old file identifies 849 records belonging to other battle objects relative to the five objects with paired previews. Legacy files lack active queue identity; queue guard coverage is provided by separate tests, not inferred from absent data.

Observe `eox.bgqc` at `0x2171BA0` with a prefix and void finalizer. Its battle is `cliq`. The native method queues its opening/counter sequence with `etw.bhej`; the later branches at `0x2172D77` and `0x21730D7` also enqueue additional `etk` steps. Each scheduler invocation gets a separate managed command with a map of step pointers. Register counter steps even when queued before the opening (preemptive order). `etk.bhdy`, `etm.bhdy` and `exk.bijb` update their own registered command. Damage is routed by current queue step and exact source/target/ability/dealer. The finalizer restores nesting without changing native exceptions. Unknown scheduler paths remain unpaired rather than being guessed into a known command.

A second queued opening no longer finalizes the first record. Multiple openings remain available in one command, with `multiple_hits` excluded from single-counter scoring. Separate commands can coexist until queue completion, timeout or battle change. Command and step identities are written in schema 2. Historical #211 was discarded before its damage was recorded; missing events cannot be recovered. Regression tests reproduce queued overlapping commands and unresolved subsequent targets without fabricating damage or claiming the original native command boundaries are known.

`AuditJournal` rotates at 16 MiB per file with a shared session id and monotonically increasing part number. It retains every previous part. Offline replay is available with `dotnet run --project tests/RetaliationHints.Tests.csproj -c Release -- --audit-replay <journal.jsonl> <report.json>`. A compact regression fixture preserves original JSON rows for all 11 false mismatches and representative excluded cases. New command hooks still require observation in subsequent ordinary gameplay; a successful replay only validates managed logic and recorded evidence.

## Passive combat audit (0.1.11)

Opt-in `Diagnostics.CombatAudit` installs separate observer hooks after the existing hash gate. Hooks are void prefixes/postfixes/finalizers: they never change arguments, return values or exceptions. No combat command or event method is invoked by the observer. Forecast math is unchanged; `AuditTrace` only captures already-computed endpoint branches.

- `etw.bhej(ety, Unit)` at `0x21EFC80` queues the action. For `etk`, capture `cmbq` (attacker), `cmbp` (ability), `cmbn` (target hex indices), `cmbo` (path). Only a single target with the same fresh visible forecast is scored. `etk.kob` at `0x21EBE50` resolves a target index through map `dpr`, confirming that it is a hex index. It is inspected, not invoked.
- `etk.bhdy` at `0x21EBF90` starts the opening attack; `cmbu` is its already-rolled luck multiplier. `etm.bhdy` at `0x21ECC50` supplies counter source `cmcf`, target `cmcg`, ability `cmcb`, multiplier `cmcd`, and pre-counter snapshots. The neutral multiplier is 1. A non-neutral multiplier on an executed strike excludes the exchange from scoring; no RNG method is called.
- `etm.bhdy` can immediately finish without a counter if either unit is dead or the ability is disabled. Observe `exk.bijb` at `0x2270650`, called after those checks, to mark actual counter execution. Merely entering `etm.bhdy` does not prove an attack occurred. Match its owner `cnaa` and the current queue step.
- `exr.bikt` at `0x2277850` is the damage application scope, with receiver `cnck` and arguments caster, cast source, dealer, input damage. The prefix stores managed snapshots. Its void finalizer removes the scope even after an exception without replacing or suppressing that exception.
- This method constructs `ObjectTookDamageEventArgs` and calls `enb.bfmq` at `0x20E7930` after applying damage, before listeners and the later `enc.bfwd` dispatch. The observer's prefix reads the actual event `damage`, `stacksDestroyed`, `immuneToDamage`, `fromMech` and immediate post-damage health. Match caster, receiver, ability, primary dealer and the queue step. Later buffs, reflection and healing cannot overwrite this snapshot.
- `etw.bheh` at `0x21EFA80` assigns `cmdt` before calling a step's `bhdy`, keeps it during its updates, and clears it after `Finished`. End an audit only when `ctwi` is false, both pending lists are empty, and the current step is absent or finished. Battle changes, overlapping attacks and a 120-second timeout produce an incomplete record.

The original 0.1.11 assumption that damage events cap overkill was disproved by the real session and corrected in 0.1.12 above. The audit separately compares ordinary health subtraction, including the existing maxInDmg cap, with immediate actual health. The native minimum-survivor cap (`stacksToLeave` in `exr.bikt`) is not added to the forecast here: its discrepancies are evidence for the next correction. Stats and buffs before the command and before the counter help investigate changes between the hits.

All JSON values are managed snapshots. No native object is serialized. Unknown linkage, missing events, multi-hit actions, unsupported forecasts and preemptive counters are not scored as successes. A match only validates the observed outcome, not every intermediate roll or the whole damage envelope. Local build and model tests do not establish that the IL2CPP observer has run in an actual battle.

## Read path

- `eof.bgdy` constructs the game's own DamageUiParams from `cldm` (caster), `cldl` (ability), target and attack-pattern multiplier. It calls `bgdp` (damage forecast) and then `bgdq` (counterattack indicator).
- `eof.bgdy(FieldObject, euk, ESideCastType)` at RVA `0x20F8A40` and an equivalent entry `eof.meg` at `0x210E260` call `bgdp` (RVA `0x20F7AC0`) and then `bgdq` (RVA `0x20F7C20`). In 0.1.6 capture no longer requires a scope around only `bgdy`. The alternate entry's existence is verified; its involvement in the user's disappearing preview is not established.
- `BhBattleUnitInfoView.bghr(evr)` receives the native outgoing endpoints. `cmpr` means valid, `cmqa` damaging; `cmps/cmpt` are the HP range. Match the actual instance against the selected target's view with `ckil.bfzc<eml>(target.ctux).ckom.cmot`, the lookup verified inside `bgdp`. A secondary splash/heal panel cannot substitute for it.
- `eox.bgqn(Unit, Unit, eib, Hex, List<Hex>)` supplies native counter eligibility. Match live hover caster, ability, target and mouse cell; join this decision with damage by all selection pointers and the same frame. Either callback order can publish. Native `bgdq` supplies `hover.clcx` as target hex and `hover.clct` as path (verified at RVA `0x20F7DAD`). Since 0.1.8 false decisions also publish, producing «Без контрудара» without running calculation. Never execute a fresh battle command to obtain eligibility.
- `Hex.clbi` / `Hex.fieldObjects` identify occupants, including large creatures. Do not require the hovered cell to equal `ctvn`. Battle instance or `elb.lastBattleId` changes invalidate both caches and the published context. Do not join data from a different selection or frame.
- `eia.bdui` selects the counter ability using the same map/blocker/path inputs as the eligibility check. For melee/range paths, element zero is the attack destination used by this native check.
- `UnitData.ctxr` (native `bijp`) counts full + temporary + wounded-top creatures. `cnbx` is the wounded top HP; `fullStacks` excludes it.
- `evs.bhyd` is the deterministic UI damage factory. It uses current unit stats, ability/dealer modifiers, native damage endpoints (`exu.biop`), caps and casualty conversion; it does not roll battle RNG or execute attacks.
- Attack pattern `charX/charY` addresses the primary target. Only positive multipliers identical across rotations are accepted. Unknown/ambiguous patterns are rejected. Counter patterns in this installation were checked against the catalog.
- `Unit.bigr("counter_before_attack")` reads the active sequence effect from native unit data/buffs.

## Isolation

The adapter uses native `MemberwiseClone` to copy Unit, UnitData, location (`enh`) and the counter ability. It only writes detached health/count/location/owner fields. Other references are read-only; copies are never initialized, placed on the map, added to a side or used in commands/events. Ability damage, RNG, saves and the game's original forecast are never patched.

No Harmony detour accepts `DamageUiParams`: that is a non-blittable IL2CPP value type. The three detours accept only native references and the primitive eligibility result.

## Health and self vampirism (0.1.6)

`UnitData.tempFullStacks` plus a temporary wounded top (`cnca && cnbx > 0`) is retained separately from permanent creatures. Detached snapshots preserve the top's temporary flag. Pure health arithmetic accounts for growth and casualties after healing; displayed casualties are not net growth/loss since before the opening attack.

The installed `flicker`/upgraded configs have a single-target `selfMechanics` vampirism after attack, using `with temp stacks`. Runtime mechanic `esm` exposes flat heal `clvu`, fraction `clvv`, allegiance `clvw`, and heal type `clvx`. Its native execution `bgty` (0x21CD9B0) is inspected but NEVER called. The adapter checks self allegiance/afterAttack, a single positive damage cell and one source. It respects `ctuw.bejl` and `eox.bgpn` (0x216DF30), then follows native truncation, `eox.bgpf` healing bonus (0x216D770), vampirism multiplier, and pure cap `exq.bikb` (0x22755F0). These helpers only read state. Never call `exq.bikc`, `bijz` or queue a healing event.

Supported modes: WithTempStacks, WithRealUntilStart without existing temporary creatures, WithoutRespawn. Multiple sources, splash healing, other modes and limitStacks are explicitly unavailable. Healing-enabled evaluation sweeps all surviving opening rolls (at most 257), because wounded-top HP can produce an interior casualty extremum. The per-calculation native forecast cache prevents repeated calls for identical projected health. Huge ranges are explicitly unavailable rather than sampled. Guaranteed lethal rolls short-circuit to no counter. Preemptive replies use the original state without healing.

Direct target mechanics other than ordinary damage, unknown self mechanics, death protection and opening hit buffs/side-dealer payloads are rejected. Both `eib.cjug/cjuh` and underlying `AbilityLogicConfig.selfDealer/allyDealer` can be allocated for empty configurations. Version 0.1.6 incorrectly used config presence; 0.1.7 checks payload instead. Native CastDealerConfig constructor (0x2D83F50) defaults statDmgMult to 1, numTargets to 1, triggerCounter to true, and supplies a pattern even without damage. These are not evidence of an effect. Require an actual buff/mechanic or nonzero damage with a configured damage target. Passive event chains are not exhaustively detected or simulated. The result remains an approximation.

## Display lifecycle correction (0.1.7)

User log confirms paired native forecasts in battles 2, 4, 6, 9 and 11, but only first placement is logged and the user sees no panel after the first battle. This rules out a blanket capture failure across subsequent battles; it does not uniquely identify a single render guard. The old guard combined missing/inactive controller and remembered ccgc under one stage name, and was logged only once per process.

Every battle generation now releases the mod widget and cached native UI; parent, font and material identities also invalidate a binding even when the host pointer remains unchanged. Native BattleUIController Awake/OnEnable assign the singleton; a read-only active-object lookup can recover when it is unusable. No native UI is initialized or activated. ccgc is written by `the(TypeBattleUI)` and is not itself a visibility flag. The mod reads registered visible BhUnitWindow/BhMagicBook/BhBattleEnd windows and log visibility instead of vetoing on that remembered value. `BhBattleLog.bisr` at 0x22A82F0 writes cnem from its open/closed argument and starts the appear animation; require cnem plus a visible canvas group. Per-battle bounded diagnostic stages distinguish capture, resolved UI, visible modals and actual text preparation. Live appearance still requires the user's confirmation.

## Visibility and approximation

The user confirmed multi-battle display in 0.1.7. In 0.1.8 they explicitly requested a visible no-counter state, superseding the old hide-on-false behavior below. Both decisions still require matching native damage and all existing hover/forecast/modal guards. The widget/cursor lifecycle is unchanged. Eligibility flips invalidate cached text immediately. Unsupported/failed calculations use one short unavailable label, while detailed reasons remain in bounded logs; they are never inferred to mean no counter. Health and vampirism arithmetic remains unchanged. The new status branch and return to numerical display await the user's gameplay check.

`eof.bgdu` invalidates only the context owned by that hover controller. Rendering also requires the same hover context and the native target forecast's visible CanvasGroup. Since 0.1.2 the widget is a child of the native screen-space cursor UI, with no separate canvas or sorting override; every Graphic has raycasts disabled. The optional simple-tooltip host's own active flag is not a visibility gate; its root canvas and the normal battle UI are.

As of 0.1.1, a false native eligibility result clears the current capture and hides the entire annotation before constructing or placing a widget. `Range` is native reaching melee; `Shoot` is the ranged shot. Do not replace native eligibility with an enum-name heuristic.

The first user screenshot exposed unsafe mixed dimensions: border insets were in native local units while the panel size was converted from pixels. Version 0.1.1 normalized those dimensions on the world-space unit bar, but the user then reported that no hint was visible despite a successful placement log. That log does not confirm actual rendering.

Version 0.1.2 resolves `Hex.UI.BattleUIController.me`, requires `ccgc == TypeBattleUI.Normal`, and reads `cszk` (the native `BhCursorTooltips`). `rootCanvasRect` is passed by the game's `BhCursorTooltips.Init` to `BhSimpleTooltip.Init` and serves as the parent coordinate space. We use the normal `simpleTooltip.targetsText.font`, without copying `BhSeeThroughTextUGUI` or its world-space shared material. The screen-space canvas must be active; ScreenSpaceCamera mode requires its real canvas camera. WorldSpace is rejected. The native tooltip object itself need not be visible.

The root normalizes both axes to screen pixels. Text, icon and one-pixel frame all use those coordinates. Placement follows `Input.mousePosition` with a clear gap, flips at screen edges and clamps to the viewport. Invalid coordinates hide the hint. No native transforms or canvases are modified. In addition to attacker, defender and attack identity, changes in destination, counter ability or native damage endpoints invalidate the cached estimate immediately; unchanged calculations retain the 0.12-second throttle.

The user's 0.1.2 screenshot confirms the frame and casualty sprite render, but the label is blank; the corresponding BepInEx log has no calculation exception. The old label used a fresh TMP component with only `font` assigned, fixed 32-pixel row height and `Ellipsis`. The game's tall font line metrics are also documented in the working Skill Synergies renderer. Version 0.1.3 assigns `simpleTooltip.targetsText.fontSharedMaterial` as well as the font (read-only references), uses nonwrapping `Overflow`, forces text mesh preparation and sizes/centers the row from actual visible glyph bounds. The measuring rectangle stays fixed so moving the label does not alter its line layout. Oversized glyph bounds reduce the label's font size to fit the available width and row height. Font assets and materials are never mutated. Content, scale, available width or reactivation invalidate this layout; mere mouse movement does not rebuild it.

Before revealing the row, the mesh must contain visible glyphs with finite positive bounds. The first placement log includes the actual forecast string, glyph count, font and material to distinguish calculation failures from rendering failures. This does not assert that the user has seen the final rendered text. Version 0.1.3 only changes the display and its diagnostics; casualty arithmetic is unchanged. Build passed; live visibility remains for the user.

The 0.1.3 test again showed no panel. That session logged plugin startup but neither a successful placement nor a display/calculation exception: the exact early guard was not recorded, so the font cannot be claimed as the sole cause. Version 0.1.4 changes capture as described above and adds at most 24 once-per-stage diagnostic lines. They distinguish updater startup, native display entry, damage capture, counter refusal/acceptance, visibility rejection, successful arithmetic and font preparation. An empty first-frame text mesh now leaves the mod root active but transparent and retries on the next frame, instead of repeatedly deactivating the TMP component. Numeric calculation is unchanged. Build and source review passed; no live gameplay verification was performed.

The damage envelope represents one retaliation under current stats. Luck rolls, passive event chains, movement-driven aura changes and other units' reactions remain outside the estimate. Therefore numeric text has `~`; this is not an exhaustive or guaranteed bound on real combat. Temporary creatures and the limited self-vampirism path are supported as of 0.1.6; death protection remains explicitly unsupported.

Local validation covers health arithmetic, ordinary and preemptive ordering, disabled/absent retaliation, lethal opening attacks, invalid forecasts and installed counterattack-pattern multipliers. Version 0.1.2 adds focused pure checks for cursor spacing and viewport edges. Native fields compile against the installed interop; the actual in-game appearance remains for the user's test after restart.
